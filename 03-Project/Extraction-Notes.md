# Multimodal Image Extraction Notes (Session 12)

**Lab 12.1 — Single Image Extraction & Quality Audit**
Model: `gemini-2.5-flash` · Script: `scripts/extract-image.js` · Date: 2026-09-24

## Sample images (both non-confidential)

Neither image contains personal, customer, or confidential data. Both are synthetic mock-ups of
equipment from this project's own vault, generated by `scripts/make-sample-images.py` so the
ground truth is known exactly and the files can be regenerated:

| File | What it is | Domain role |
|---|---|---|
| `sample-images/a.jpg` | Photo-style shot of the `NetGate Home X2` router's rear label (sticker on dark plastic, tilted ~1.6°) | Device identification — the vault says "match the model label before applying a manual procedure" |
| `sample-images/b.png` | Handwritten field note on lined paper, plus a hand-drawn network sketch | Symptom intake and topology capture |

Commands run (once per image, before and after the prompt change):

```bash
npm run extract-image -- ./sample-images/a.jpg
npm run extract-image -- ./sample-images/b.png
```

> Reliability note: the API returned `503 UNAVAILABLE` ("model is currently experiencing high
> demand") on roughly half of the runs. The script has no retry, so a run fails hard and must be
> repeated. Individual results below are from successful runs.
>
> The free tier then also hit its **daily** cap: `429 RESOURCE_EXHAUSTED`, "Quota exceeded for
> limit: 20, model: gemini-2.5-flash". The limit is per model per project, so the extractor can be
> moved off an exhausted model with `GEMINI_MODEL=gemini-2.5-flash-lite` and no code change.
> A per-day quota is not worth retrying — it resets in hours, not seconds — so `isRetryableError`
> now fails fast on it instead of burning four backoff attempts. `scripts/extract-image.js` still
> calls the API directly and so still prints a raw stack trace on failure, while the folder and
> upload paths degrade in a readable way.

## Image 1 Evaluation (`sample-images/a.jpg`)

**Ground truth actually visible in the image:** vendor `NETGATE`, "Home X2 Wireless Router",
MODEL `Home X2`, S/N `NGX2-4471-A9`, MAC `8C:1F:64:2A:0B:D3`, SSID `NetGate-4471`,
WEBUI `http://192.168.1.1`, INPUT `12V DC 1.5A`, FCC ID `2AX9F-HX2`, MADE IN `VIETNAM`, plus a
1D barcode with no human-readable digits.

### Baseline prompt output

```json
{
  "title": "NETGATE Home X2 Wireless Router",
  "summary": "Product label providing essential identification and configuration details for a NETGATE Home X2 wireless router.",
  "key_points": [
    "Model: Home X2",
    "Serial Number (S/N): NGX2-4471-A9",
    "MAC Address: 8C:1F:64:2A:0B:D3",
    "SSID (Wi-Fi Name): NetGate-4471",
    "Web UI (Access Address): http://192.168.1.1"
  ]
}
```

### Audit

- **Extracted perfectly:** vendor, model, serial, MAC, SSID and WEBUI — all six transcribed
  character-for-character, including the colons in the MAC. `doc_type` aside, nothing was misread.
- **Missing:** the power rating `12V DC 1.5A`, `FCC ID 2AX9F-HX2`, and `MADE IN VIETNAM` are all
  clearly legible but absent. The `up to 5` key-point cap forced prioritisation, and the
  regulatory/electrical fields lost. The barcode was never mentioned at all.
- **Hallucinated/Invented:** none. The summary's "identification and configuration details" is a
  fair characterisation of the label, not new content.
- **Format:** failed the "ONLY valid JSON" instruction — the reply was wrapped in a ` ```json `
  fence, so `JSON.parse` on the raw text would throw.

### Prompt Revision

The baseline was generic; the revision (now committed in `scripts/extract-image.js`) targets this
product domain specifically:

1. Role set to "intake step of a local hardware troubleshooting assistant".
2. Explicit anti-invention rules: use `null` / omit rather than fill gaps; never supply a plausible
   date, name, or model number.
3. Identifiers must be copied character-for-character — no reformatting or "correcting".
4. Reading must include handwriting and any diagram/box/label in the image (the baseline ignored
   the sketch entirely — see Image 2).
5. A domain schema replacing free-form `key_points`: `doc_type`, `title`, `summary`,
   `device{vendor, model, serial, mac_address, ip_addresses}`, `symptoms`, `actions_attempted`,
   `warnings`, `next_steps`, `measurements_and_times`, `diagram`, `uncertain`.
6. `uncertain[]` created as an explicit escape hatch for unreadable or guessed content, so
   guessing has somewhere to go instead of silently becoming fact.

### Post-revision output

```json
{
  "doc_type": "device_label",
  "title": "NETGATE Home X2 Wireless Router",
  "summary": "A device label for a NETGATE Home X2 router, model Home X2, with serial number NGX2-4471-A9, MAC address 8C:1F:64:2A:0B:D3, and default SSID NetGate-4471. The device's WEBUI is http://192.168.1.1 and it requires 12V DC 1.5A input power.",
  "device": {
    "vendor": "NETGATE",
    "model": "Home X2",
    "serial": "NGX2-4471-A9",
    "mac_address": "8C:1F:64:2A:0B:D3",
    "ip_addresses": ["192.168.1.1"]
  },
  "symptoms": [],
  "actions_attempted": [],
  "warnings": [],
  "next_steps": [],
  "measurements_and_times": ["12V DC 1.5A"],
  "diagram": null,
  "uncertain": []
}
```

**Did it improve? Yes, partially.**

- Field-level accuracy is now machine-usable: the six identifiers land in named `device.*` slots
  instead of being buried in prose, which is what a troubleshooting agent actually needs to match
  a label against `Device-Inventory.md`.
- The power rating is now recovered (`measurements_and_times`), so the schema change did fix one
  real omission.
- Still missing: `FCC ID 2AX9F-HX2`, `MADE IN VIETNAM`, and the barcode is still unmentioned
  (not even listed in `uncertain`). The schema has no slot for regulatory fields, so they have
  nowhere to land — the omission moved from "capped list" to "no field", not to "fixed".
- That omission is itself unstable. A later identical re-run named *both* `FCC ID 2AX9F-HX2` and
  "MADE IN VIETNAM" in `summary`, because with no dedicated slot the model surfaces them only when
  it happens to describe the whole label. A `regulatory` slot would make their presence reliable
  instead of luck.
- Formatting was not stable either: this run came back fenced in ` ```json `, while an identical
  later re-run returned bare JSON (see the format-compliance note below).
- No new hallucinations; `device.model` is correctly `Home X2` and not the marketing line.

## Image 2 Evaluation (`sample-images/b.png`)

**Ground truth actually visible in the image:** title "Printer down - check!"; office printer
(LaserPro 2400) not printing since 08:40; router LED blinking amber about 10 min, was solid blue;
tried a printer power cycle and a patch-cable swap with no change; ping `192.168.1.50` = no reply,
ping `192.168.1.1` = OK; the WAN cable at the router looks loose, reseat it first; "DO NOT factory
reset the router. Config backup not confirmed!"; if still down by 5pm escalate to the on-call
technician. Sketch: `WAN` cloud → `router 192.168.1.1` → branches to `printer 192.168.1.50` and
`NAS 192.168.1.60`. There is no date on the note and no author's name.

### Baseline prompt output

```json
{
  "title": "Printer Down - Check!",
  "summary": "The office printer (LaserPro 2400) has been offline since 08:40 and is unreachable via its IP (192.168.1.50). The router's LED is blinking amber, though the router itself is reachable. Basic troubleshooting steps (power cycle, cable swap) have not resolved the issue.",
  "key_points": [
    "Office printer (LaserPro 2400) not printing since 08:40; its IP (192.168.1.50) is unreachable.",
    "Router LED is blinking amber (previously solid blue); router IP (192.168.1.1) is reachable.",
    "Initial troubleshooting (power cycle printer, swapped patch cable) had no effect.",
    "Next step: Reseat the WAN cable at the router, as it appears loose.",
    "DO NOT factory reset the router (config backup not confirmed). If still down by 5 PM, escalate to on-call technician."
  ]
}
```

### Audit

- **Extracted perfectly:** every handwritten line read correctly — the model name, both timestamps,
  the LED states, both ping results, the loose-WAN-cable observation, the factory-reset warning,
  and the 5pm escalation. Handwriting accuracy was effectively 100% on this note.
- **Missing:** the entire sketch. `192.168.1.60` (the NAS) never appears, and there is no record
  that the image contains a topology at all. For a bot that is supposed to reason about *this*
  network, losing a node is a real gap.
- Quality of structure: symptoms, actions tried, warnings and next steps are all flattened into one
  ranked list, so a downstream agent cannot tell "do not factory reset" (a hard constraint) from
  "printer is offline" (an observation).
- **Hallucinated/Invented:** nothing fabricated. Two mild inferences: "offline" for "not printing"
  (supported by the failed ping) and Title-Casing "5 PM". No invented date, technician name, or
  procedure. Notably the model did **not** invent an E13 error code or any printer-manual step,
  which is exactly the failure mode this project is trying to avoid.

### Prompt Revision

Same revision as Image 1 (single shared prompt). For this image the relevant additions were the
handwriting/diagram reading rule (rule 4) and splitting symptoms, actions, warnings, next steps and
measurements into separate arrays.

### Post-revision output

```json
{
  "doc_type": "handwritten_note",
  "title": "Printer down - check!",
  "summary": "The office printer (LaserPro 2400) is not printing since 08:40. The router's LED has been blinking amber for about 10 minutes, after being solid blue. The WAN cable at the router appears loose. Attempts to power cycle the printer and swap its patch cable were made, and a ping to the printer's IP (192.168.1.50) received no reply, though a ping to the router's IP (192.168.1.1) was successful.",
  "device": {
    "vendor": "LaserPro",
    "model": "2400",
    "serial": null,
    "mac_address": null,
    "ip_addresses": ["192.168.1.50", "192.168.1.1", "192.168.1.60"]
  },
  "symptoms": [
    "Office printer (LaserPro 2400) not printing since 08:40.",
    "Router LED = blinking amber about 10 min.",
    "WAN cable at router looks loose",
    "Ping 192.168.1.50 = no reply."
  ],
  "actions_attempted": ["power cycle printer", "swapped the patch cable", "Ping 192.168.1.50", "Ping 192.168.1.1"],
  "warnings": ["DO NOT factory reset the router. Config backup not confirmed!"],
  "next_steps": ["reseat it first.", "If still down by 5pm, escalate to the on-call technician."],
  "measurements_and_times": ["since 08:40", "blinking amber about 10 min.", "Was solid blue.", "Ping 192.168.1.1 = OK.", "by 5pm"],
  "diagram": ["WAN -- router", "router -- printer", "router -- NAS"],
  "uncertain": []
}
```

**Did it improve? Yes, clearly.**

- The sketch was rescued: `192.168.1.60` now appears in `device.ip_addresses` and the three diagram
  edges are captured. This is the single biggest win of the revision.
- The "DO NOT factory reset" constraint is now isolated in `warnings[]`, where a safety gate can
  treat it as binding — the exact distinction this product needs (see `Safety-Escalation.md`).
- Actions tried are separated from symptoms, which makes "what has already been ruled out"
  queryable instead of re-suggested.
- **New (small) hallucination introduced:** the image never labels a vendor or model field, yet the
  model filled `device.vendor = "LaserPro"` and `device.model = "2400"` by splitting the printer's
  name in the prose. The split happens to be correct, but it is inference presented as extracted
  fact — the schema gave it a slot to fill and rule 1 did not prevent it. `serial` and `mac_address`
  were correctly left `null`.
- `next_steps[0]` lost its subject: `"reseat it first."` is a fragment whose antecedent ("the WAN
  cable") only exists in `symptoms`. Verbatim quoting traded context for faithfulness.
- `uncertain` stayed empty even though `doc_type` mapping and the vendor/model split were both
  judgement calls.
- Again fenced in ` ```json ` — rule 5 was ignored on both images in this round, though the fence
  turns out to be intermittent rather than absolute (see the format-compliance note below).

## Summary of Multimodal Performance

- **JSON Format Compliance:** Partial, and *nondeterministic*. The reply is schema-shaped and
  parseable once any ` ```json ` fence is stripped, and `parseModelJson` now does that stripping
  automatically. But instructing "Return ONLY the raw JSON object ... no markdown code fences" did
  not make the fence go away: it appeared in most runs and was simply absent in others, with the
  same image and the same prompt. Format is therefore a harness concern, not a prompt concern —
  which is exactly why the API-level `responseMimeType` fix (follow-up 1) is the reliable answer.
- **OCR Accuracy:** High — 100% of printed label identifiers on Image 1 and 100% of the handwriting
  on Image 2, including `8C:1F:64:2A:0B:D3`, `NGX2-4471-A9`, and `192.168.1.60` read only from the
  sketch.
- **Hallucination rate:** Low, but non-zero after the revision. Zero in the baseline (which simply
  dropped hard-to-place content); one schema-driven fabrication (`vendor`/`model`) once structured
  slots existed. *Giving a model empty fields to fill increases invention risk* — the `null` rule
  needs to be stated per-field, not once in the preamble.
- **Net effect of the prompt revision:** strict recall gain (recovered the power rating, the sketch
  node, the diagram edges, and the warning/next-step split) with one small precision loss. For a
  troubleshooting assistant, that trade is the right way round: missing a network node is worse
  than a redundant correct vendor string.

## Lab 12.2 — Batch extraction (`npm run extract-folder`)

Two images were already present (`a.jpg`, `b.png`), so no duplication was needed.

### First run, using the kit script as provided: total failure

```text
Processing 1/2: a.jpg
Processing 2/2: b.png
ApiError: {"error":{"code":503,... "status":"UNAVAILABLE"}}
```

No file was written at all — not even the `a.jpg` result that had already succeeded. Three defects
surfaced in that one run:

1. **No retry.** A transient `503` (the same capacity error that hit roughly half of the Lab 12.1
   runs) aborted the whole batch *after* the first image had been processed and paid for.
2. **Divergent prompt.** `extract-folder.js` still carried the old generic
   title/summary/key_points prompt, so batch and single-file extraction did not produce comparable
   data.
3. **The payload was not structured data.** Each entry stored `data: response.text` — a *string*
   containing fenced JSON. The file would have been technically valid JSON, but every `data` value
   would have been prose-wrapped text rather than an object.

### Fix

Added `lib/extraction.js` as the single source of truth: the domain prompt, `mimeFor`,
`parseModelJson` (strips fences, slices the outermost braces, preserves `rawText` on failure) and
`extractImageJson` (retry with exponential backoff plus jitter on 429/500/502/503/504). Both
scripts now import it, so they can no longer drift apart. `extract-folder.js` also isolates
per-file failures: one bad image produces a `{ file, data: null, error }` entry and a non-zero exit
code instead of destroying the run, and an unparseable reply keeps its raw text rather than being
silently dropped.

### Verified result

```text
Processing 1/2: a.jpg (gemini-2.5-flash)
  transient error — retry 1 in 1667ms
  ok (after 2 attempts)
Processing 2/2: b.png (gemini-2.5-flash)
  ok
Saved 2 results (0 failed) → extracted-data.json
```

The retry was exercised for real on `a.jpg`, and the run finished with zero failures.

`extracted-data.json` validates as a JSON array of 2 entries — one per image in the folder, both
with `data` parsed into structured objects of 11 fields:

| Entry | doc_type | IPs recovered |
|---|---|---|
| `a.jpg` | `device_label` | `192.168.1.1` |
| `b.png` | `handwritten_note` | `192.168.1.50`, `192.168.1.1`, `192.168.1.60` |

The batch run also reproduced the Lab 12.1 findings, which raises confidence they are systematic
rather than one-off: `b.png` again recovered the NAS `.60` node from the sketch along with all
three diagram edges, again isolated the factory-reset warning in `warnings[]`, and again inferred
`device.vendor = "LaserPro"` / `model = "2400"` from prose that never labels a vendor field.

### New issues seen only in batch mode

- **Schema misuse:** `a.jpg` filed `"barcode"` inside the `diagram` array. That slot is for diagram
  nodes and links, so an unlabeled graphic was recorded as network topology — downstream code
  reading `diagram` as topology would be misled.
- **Run-to-run variance:** the single-file run titled `a.jpg` "NETGATE Home X2 Wireless Router";
  the batch run titled it "NETGATE", obeying "headline exactly as written" by taking the brand
  alone. Overlapping triage notes differ as well (`b.png` symptoms dropped "since 08:40" here,
  though it survived in `summary` and `measurements_and_times`). Same image and same prompt,
  different shape — worth knowing before anything keys off `title`.
- **The same instability hit the invented `device` slot.** Across three runs of `b.png` the
  unlabeled printer name came back three different ways: `vendor: "LaserPro"` / `model: "2400"`
  twice, then `vendor: null` / `model: "LaserPro 2400"` on a post-refactor re-run. Field-level
  output for content the image does not label is not reproducible, which is the strongest argument
  for removing the empty slot (follow-up 4) rather than trusting the `null` rule.
- `extracted-data.json` is already listed in `.gitignore`, so it stays a generated artifact rather
  than something to commit.

## Session 12 Stretch — browser upload (`POST /extract-image`)

The core lab processes local files through terminal scripts. The same extraction now also runs over
HTTP, so a photo can be uploaded straight from the UI instead of dropped into `sample-images/`.

### What was built

- **`public/index.html`** — an `<input type="file">` form (accepting PNG/JPEG/WebP) that POSTs the
  image as `multipart/form-data` and pretty-prints the returned JSON, with a metadata line showing
  filename, size, `doc_type`, and how many model calls were used.
- **`server.js`** — `POST /extract-image` using `multer.memoryStorage()`, so the upload is buffered
  in memory only and never touches disk (`fileSize` cap 8 MB, single file, MIME allow-list). The
  bytes are base64-encoded and handed to the same prompt/parser/retry stack the CLI scripts use.
- **`lib/extraction.js`** — refactored so `extractImageJson` (disk) and
  `extractImageJsonFromBuffer` (memory) share one `generateWithRetry` body. No prompt duplication,
  and the web path inherits the 503 retry and JSON-fence stripping for free.
- A JSON error middleware, so multer failures (oversized file, rejected type) return JSON rather
  than an HTML error page the frontend cannot read.

### Verified behaviour

| Request | Result |
|---|---|
| `POST /extract-image` with `sample-images/a.jpg` | `200` — full 11-field object, 1 model call |
| `POST /extract-image` with a `.json` file | `400` — `Unsupported image type: application/octet-stream...` |
| `POST /extract-image` with no file | `400` — `No image uploaded. Send a file in the "image" field.` |
| `POST /extract-image` with a 9 MB file | `413` — `File too large` |

The browser path was then driven end-to-end in the Preview tab — a canvas-drawn label injected as a
real `File` into the actual form, since a native file picker cannot be scripted here. The DOM
rendered `doc_type: device_label`, `serial: LP24-8891-B2`, `mac_address: 44:38:39:00:1B:7E`,
`ip_addresses: ["192.168.1.50"]` and `symptoms: ["Error: E13 paper jam"]` from a 13.2 kB upload, in
one model call, with a single `POST → 200` in the network log and no console errors.

### Gotcha found while wiring this up

This environment sets `PORT=0`, so `app.listen(0)` bound a *random* ephemeral port while the startup
banner still printed `http://localhost:3000`. The app looked broken; it just was not where it claimed
to be. The banner now reports `server.address().port` — the port actually bound.

### Residual risk

`POST /extract-image` is unauthenticated, so anyone who can reach the server can spend API quota and
upload arbitrary images. Acceptable for a local lab; it needs auth plus rate limiting before it is
exposed anywhere real.

## Follow-up fixes worth making

1. **Enforce JSON at the API level** — set `responseMimeType: 'application/json'` (and optionally a
   `responseSchema`) in `generateContent`. `parseModelJson` now *tolerates* fenced replies, but the
   API flag would make a malformed reply fail loudly instead of being quietly repaired.
2. ~~Retry with backoff on 503/429~~ — **done**, in `lib/extraction.js`.
3. **Add the missing schema slots** — a `regulatory` object (`fcc_id`, `country_of_origin`), an
   `ssid` field, and either a separate `graphic` field or tighter wording on `diagram`, so Image 1's
   FCC ID and "MADE IN VIETNAM" have somewhere to land and a barcode stops being filed as
   topology.
4. **Stop using one prompt for every image type** — a label, a note, and a screenshot want
   different schemas; branching on `doc_type` (or asking for it first) would remove the
   `LaserPro`/`2400` style inference.
5. ~~Mirror the prompt into `scripts/extract-folder.js`~~ — **done**; both scripts share
   `lib/extraction.js`, as does `POST /extract-image`.
6. **Guard `/extract-image`** — add auth and a rate limit before this endpoint leaves localhost.
